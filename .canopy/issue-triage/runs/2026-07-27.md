## Findings the issues themselves did not account for

Both surfaced during verification, and both are **hand-backs, not absorbed into this run**:

1. **A step inside the `pytest` job would be advisory, not a gate.** Branch
   protection on `main` requires exactly one context — `check-version`
   (`enforce_admins: true`, verified via the protection API). A step appended to
   the existing `pytest` job rides under the `pytest` check, which is *not*
   required, so a structural regression would redden the PR and still merge. By
   #389's own thesis ("a warning nobody's build fails on is how the 1090-char
   description sat there"), a *check* nobody's merge fails on is the next version
   of that hole. Hence: **separate `structure-drift` job** with its own
   addressable context name — mirroring `check-version`'s shape — so the context
   can be added to branch protection. That protection change is a repo-admin
   settings edit, outside the code and not verifiable in-session.

2. **The budget check has a blind spot exactly where the failure class is live.**
   `check_skill_description_budget` (`structure_drift.py:299-305`) globs
   `plugins/canopy/skills/*/SKILL.md` **only** — `agents/` and `commands/` are
   never measured. `plugins/canopy/agents/ddd.md` carries a **1134-char**
   description, over the 1024 cap *right now*, and the audit is still clean
   because nothing looks there. Widening the check would surface it — which turns
   "add a CI step" into "add a step **and** trim an over-cap agent description,"
   and would red-fail the new gate until that trim lands. Deliberately kept
   **out** of this run's PR so the gate ships green; filed as the recommended
   follow-up.

   Headroom on the skills that *are* measured is thin but adequate:
   `ddd-concept-eval` 953/1024, `ddd-upload` 935, `ddd-findings-review` 927.
